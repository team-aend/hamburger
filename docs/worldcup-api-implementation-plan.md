# 햄버거 월드컵 API 세부 구현 계획

## 1. 목적과 현재 상태

기존 `products`를 참가 버거로 사용하고, 월드컵 진행·경기 결과를 저장할 테이블과 API를 추가한다. 대진과 승자는 서버에서 검증하며, 완료된 월드컵을 기준으로 실제 랭킹을 집계한다.

계획 작성 당시 코드 확인 결과:

- PostgreSQL 스키마, Supabase 연결 풀, 초기 데이터 입력 스크립트가 있다.
- 검색 API는 아직 DB 조회 대신 `backend/src/data/database.ts` 배열을 사용한다.
- 월드컵은 프론트의 가상 버거 데이터로 진행되며 결과를 저장하지 않는다.
- 랭킹 화면은 목업 통계를 사용한다.
- 실제 Supabase에 테이블과 데이터가 적용됐는지는 별도로 접속 검증해야 한다.

이 문서는 구현 계획이며 API 및 DB 변경이 완료되었다는 의미는 아니다.

## 2. 1차 구현 범위

| 항목 | 기준 |
|---|---|
| 참가 단위 | 상품 `products` 기준. 단품·세트는 같은 버거로 취급 |
| 참가 대상 | 햄버거 카테고리, `ACTIVE` 상품, 활성 브랜드 |
| 강수 | 8강·16강 |
| 대진 구성 | 서버에서 중복 없이 무작위 추출 및 배치 |
| 진행 방식 | 한 경기씩 선택을 저장하고 다음 경기 반환 |
| 로그인 | 로그인 없이 익명 세션 사용 |
| 새로고침 | 같은 익명 세션에서 진행 상태 복원 |
| 랭킹 반영 | 끝까지 완료한 월드컵만 반영 |
| 중도 종료 | 종료 상태로 보관하고 랭킹에서는 제외 |

상품 수가 선택한 강수보다 적으면 서버에서 시작을 거절하고 프론트에서도 해당 강수를 비활성화한다.

검색 API 전체의 DB 전환은 이번 범위에서 분리한다. 이후 같은 상품 조회 모듈을 공유할 수 있도록 설계한다.

## 3. 기존 상품 데이터 활용

| 카드 정보 | 데이터 출처 |
|---|---|
| 상품 ID·이름·설명·이미지 | `products` |
| 브랜드 이름 | `brands` |
| 햄버거 여부 | `categories.slug = 'burger'` |

- 가격·영양정보는 최초 버전의 월드컵 필수 항목에서 제외한다.
- 추후 가격·영양정보를 표시하면 활성 단품 옵션을 기준으로 조회한다.
- 기존 가상 버거 ID와 DB 상품 ID를 이름으로 매칭하지 않는다. 월드컵과 랭킹 모두 DB 상품 ID 기준으로 전환한다.
- 이미지가 없는 상품에는 공통 버거 이미지를 표시한다.

## 4. 추가 테이블

### 4.1 `worldcup_sessions`

월드컵 한 번의 진행 상태를 저장한다.

| 필드 | 역할 |
|---|---|
| `id` | 세션 식별자 |
| `owner_token_hash` | 익명 소유자 토큰 해시 |
| `round_size` | 최초 강수: 8 또는 16 |
| `status` | 진행·완료·중단·만료 상태 |
| `winner_product_id` | 최종 우승 상품, 완료 전에는 NULL |
| `created_at` | 시작 시각 |
| `completed_at` | 완료 시각 |
| `expires_at` | 진행 세션의 만료 시각 |

### 4.2 `worldcup_entries`

최초 참가 버거와 대진 순서를 저장한다.

| 필드 | 역할 |
|---|---|
| `session_id` | 소속 세션 |
| `product_id` | 참가 상품 |
| `seed_position` | 최초 대진 위치 |
| 상품 표시 정보 스냅샷 | 시작 당시 상품 이름·브랜드·이미지 등 |

### 4.3 `worldcup_matches`

경기별 대진과 선택 결과를 저장한다.

| 필드 | 역할 |
|---|---|
| `id` | 경기 식별자 |
| `session_id` | 소속 세션 |
| `round_size` | 해당 경기의 라운드 |
| `match_index` | 라운드 내 경기 순서 |
| `left_product_id` | 왼쪽 참가 상품 |
| `right_product_id` | 오른쪽 참가 상품 |
| `winner_product_id` | 선택한 승자, 선택 전에는 NULL |
| `decided_at` | 선택 확정 시각 |

### 4.4 무결성 및 마이그레이션

- 동일 세션 내 같은 상품과 대진 위치는 중복 불가.
- 동일 세션·라운드·경기 번호는 중복 불가.
- 양쪽 참가자는 서로 달라야 하며 해당 세션의 참가 상품이어야 한다.
- 승자는 해당 경기의 두 상품 중 하나만 가능하다.
- 세션의 최종 우승 상품은 결승 결과와 일치해야 한다.
- 과거 기록이 있는 상품은 물리 삭제 대신 상품 상태를 변경한다.
- 시작 당시 표시 정보를 저장해 상품 정보 변경 후에도 진행 화면을 유지한다.
- 세션별 경기 조회, 완료 세션 집계, 상품별 참가 조회에 필요한 인덱스를 추가한다.
- 스키마 변경은 별도 마이그레이션 파일로 관리한다. 운영 배포마다 전체 시드를 실행해 기존 데이터를 덮어쓰지 않는다.

## 5. API 명세

기본 경로: `/api/worldcup`

| 메서드 | 경로 | 기능 |
|---|---|---|
| GET | `/options` | 참가 가능 상품 수와 사용 가능한 강수 조회 |
| POST | `/sessions` | 세션 생성, 참가 상품 선정, 첫 경기 반환 |
| GET | `/sessions/:id` | 진행 상태·현재 경기 또는 최종 결과 조회 |
| POST | `/sessions/:id/matches/:matchId/vote` | 선택 저장 및 다음 경기 반환 |
| POST | `/sessions/:id/abandon` | 진행 중인 월드컵 종료 |
| GET | `/rankings` | 실제 우승 횟수·승률 랭킹 조회 |

### 시작 요청 예시

```json
{
  "roundSize": 8
}
```

### 선택 요청 예시

```json
{
  "winnerProductId": "3"
}
```

### 응답 원칙

- 세션 관련 응답에는 `sessionId`, `status`, `progress`를 포함한다.
- 진행 중이면 `currentMatch`, 완료되면 `winner`를 반환한다.
- PostgreSQL `BIGINT` 상품 ID는 API에서 문자열로 통일한다.
- 클라이언트가 임의로 대진이나 최종 우승자를 제출하는 구조는 사용하지 않는다.
- 잘못된 요청, 소유권 오류, 만료, 이미 처리된 경기의 상충 요청을 구분할 수 있는 오류 코드를 정의한다.

## 6. 경기 진행과 중복 요청 처리

선택 API는 아래 작업을 하나의 DB 트랜잭션으로 수행한다.

1. 익명 세션 소유권 확인.
2. 세션 행을 잠가 동시 선택 요청을 직렬화하고 상태·만료 여부 확인.
3. 현재 경기인지, 선택 상품이 해당 경기 참가자인지 검증.
4. 경기 승자 저장.
5. 라운드가 끝났으면 승자들로 다음 라운드 생성.
6. 결승이 끝났으면 세션 완료와 최종 우승자 저장.
7. 트랜잭션 커밋 후 다음 경기 또는 완료 결과 반환.

멱등성 정책:

- 같은 경기에 같은 선택을 재전송하면 성공 응답을 반환한다.
- 이미 저장된 선택과 다른 상품을 보내면 `409 Conflict`로 처리한다.
- 중복 요청 확인을 현재 경기 검증보다 먼저 처리해, 이미 다음 경기로 진행된 후의 재시도도 성공시킨다.
- 네트워크 재시도나 더블클릭으로 우승 횟수가 증가하지 않도록 한다.
- 세션 생성에도 요청 식별자를 적용해 시작 요청 재시도로 세션이 중복 생성되지 않게 한다.
- 중단·완료·만료 처리와 선택 요청이 경합해도 상태가 일관되도록 동일한 잠금 규칙을 적용한다.

## 7. 실제 랭킹 집계

초기에는 별도 누적 카운터 없이 경기·세션 데이터에서 SQL로 집계한다.

| 지표 | 계산 기준 |
|---|---|
| 우승 횟수 | 완료된 세션의 최종 우승 횟수 |
| 참가 횟수 | 완료된 세션에 참가한 횟수 |
| 대결 횟수 | 완료된 세션에서 치른 경기 수 |
| 대결 승률 | 대결 승리 수 ÷ 대결 횟수 × 100 |

조회 정책:

- 8강·16강은 기본 통합하되 `roundSize` 필터를 제공한다.
- 우승 횟수 또는 승률 정렬을 지원한다.
- 같은 원본 수치는 공동 순위로 표시하고, 표시 순서는 상품 ID로 고정한다.
- 검색 후에도 전체 집계 순위를 유지한다. 순위 계산 이후 검색 필터를 적용한다.
- 대결 이력이 없으면 승률은 `null`, 화면에는 `—`를 표시한다.
- 승률 옆에 대결 수를 표시해 적은 표본임을 알 수 있게 한다.
- 진행·중단·만료 세션은 집계에서 제외한다.
- 랭킹 데이터가 없으면 샘플 수치 대신 첫 참여 안내를 표시한다.
- 데이터 규모가 커지면 실행 계획을 확인한 뒤 집계 캐시 또는 별도 통계 테이블을 검토한다.

## 8. 프론트 연동

| 화면·상황 | 변경사항 |
|---|---|
| 시작 화면 | 가능한 강수를 API에서 조회 |
| 시작 버튼 | 세션 생성 API 호출 |
| 경기 카드 | 선택 API 성공 후 다음 경기로 전환 |
| 요청 중 | 카드 선택을 잠시 비활성화 |
| 요청 실패 | 현재 경기를 유지하고 재시도 제공 |
| 새로고침 | 저장된 세션 ID로 서버 진행 상태 복원 |
| 결과 화면 | 서버가 확정한 우승자 표시 |
| 랭킹 화면 | 목업 데이터를 실제 조회 API로 교체 |
| 중도 종료 | 종료 확인 후 abandon API 호출 |

랭킹 메뉴는 추가하지 않고, 기존 월드컵 시작·완료 화면의 ‘랭킹 확인하기’ 버튼을 유지한다.

## 9. DB 연결 및 접근 제어

### 연결 설정 정비

계획 작성 당시 `backend/src/db/pool.ts`에 비밀번호가 포함된 기본 접속 문자열이 하드코딩되어 있었다. 구현 전에 다음 조치를 수행한다.

- 노출된 DB 비밀번호 교체.
- 기본 접속 문자열 제거, 서버의 `DATABASE_URL`로만 연결.
- 환경변수가 없으면 명확한 설정 오류 반환.
- 로그와 문서에 비밀번호·접속 문자열을 출력하지 않음.
- 코드 삭제만으로 Git 이력에 남은 자격증명이 무효화되지는 않으므로 비밀번호 교체가 필요함.
- 배포 환경에 맞는 TLS 인증서 검증과 연결 풀 크기·타임아웃 설정 점검.

### 익명 세션 및 권한

- HttpOnly 쿠키의 토큰으로 세션 소유권을 확인하고 DB에는 토큰 해시만 저장한다.
- 배포 환경에서 Secure·SameSite 쿠키 설정과 변경 요청의 출처 검증을 적용한다.
- DB 테이블은 Express를 통해 접근한다.
- Supabase 공개 API에서 월드컵 기록을 직접 수정할 수 없도록 테이블 권한과 RLS 설정을 확인한다.
- 서버 DB 계정에는 필요한 최소 권한을 부여한다.
- 반복 세션 생성·투표 요청 제한을 적용한다.

익명 방식만으로 한 사람이 여러 월드컵을 수행하는 것까지 완전히 방지하지는 못한다. 1차 버전의 통계는 고유 사용자 수가 아닌 ‘완료된 플레이 수’를 기준으로 정의한다.

| 단계 | 작업 | 완료 기준 |

| 1 | 연결 설정 정비·DB 상태 확인 | 환경변수 연결 및 기존 상품 조회 성공 |
| 2 | 테이블·제약·인덱스 추가 | 마이그레이션 적용, 중복 데이터 차단 |

| 5 | 프론트 연동 | 새로고침·재시도·결과·랭킹 흐름 확인 |

## 11. 검증 계획

### API 및 DB 통합 테스트

- 참가 상품 중복 없음, 허용 강수와 참가 수 검증.
- 비활성 브랜드·상품과 다른 카테고리 제외.
- 8강 7경기, 16강 15경기 이후에만 완료 처리.
- 다른 사용자의 세션 조회·선택·종료 차단.
- 해당 경기에 참가하지 않은 상품 선택 차단.
- 동일 선택 재시도, 서로 다른 동시 선택 요청 처리.
- 완료 응답 유실 후 재시도해도 결과가 중복 집계되지 않음.
- 중단·만료 세션의 랭킹 집계 제외.
- 결승 저장 도중 오류 발생 시 전체 롤백.
- 우승 횟수·승률·공동 순위·강수 필터·검색 후 순위 유지 검증.

### 화면 및 회귀 테스트

- 시작 → 선택 → 다음 라운드 → 우승 → 랭킹 이동.
- 새로고침 후 진행 복원.
- 느린 응답·통신 실패 시 중복 선택 방지와 재시도.
- 참가 수 부족, 이미지 없음, 랭킹 데이터 없음 상태.
- 기존 버거 검색 필터·랜덤 추천 기능 유지.
- `npm run build`로 프론트·백엔드 빌드 및 타입 검사.

## 12. 구현 전 확정할 세부 정책
