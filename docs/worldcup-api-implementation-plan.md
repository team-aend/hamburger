# 햄버거 월드컵 API별 구현 계획

## 문서 목적과 작업 방식

이 문서는 API를 한 번에 구현하지 않고 **아래 순서대로 API 하나씩 구현·검증·커밋**하기 위한 명세다. 각 단계에서는 해당 API에 필요한 DB 변경과 공통 코드만 추가한다. 다음 API는 현재 API의 완료 기준을 충족한 뒤 별도 작업으로 진행한다.

| 순서 | API | 해당 단계에서 완료할 기능 |
|---|---|---|
| 1 | `GET /api/worldcup/options` | 참가 대상과 가능한 강수 조회 |
| 2 | `POST /api/worldcup/sessions` | 익명 소유권 확보, 세션·참가자·첫 라운드 생성 |
| 3 | `GET /api/worldcup/sessions/:id` | 서버에 저장된 진행 상태 복원 |
| 4 | `POST /api/worldcup/sessions/:id/matches/:matchId/vote` | 선택 저장, 다음 라운드 진출, 우승 확정 |
| 5 | `POST /api/worldcup/sessions/:id/abandon` | 진행 중 월드컵 중단 |
| 6 | `GET /api/worldcup/rankings` | 완료한 월드컵의 실제 랭킹 조회 |

각 API는 테스트용 DB의 고정 데이터로 독립 검증한다. 앞 단계에서 다음 API를 미리 구현하지 않는다. 선택·복원·종료 API가 준비되기 전에는 기존 월드컵을 부분적으로 서버 방식으로 전환하지 않는다. 개별 API 검증을 마친 뒤 전체 사용자 흐름을 연결한다.

## 공통 전제

### 현재 상태

계획 작성 당시 PostgreSQL 스키마, Supabase 연결 풀, 초기 데이터 입력 스크립트가 존재한다. 검색 API는 `backend/src/data/database.ts` 배열을 사용하며 월드컵·랭킹은 프론트 목업 데이터로 동작한다. 실제 Supabase 스키마·시드 적용 여부는 별도로 확인해야 한다.

### 비즈니스 원칙

- 참가 단위는 `products`다. 단품·세트 옵션을 별도 참가자로 취급하지 않는다.
- `categories.slug = 'burger'`, `products.status = 'ACTIVE'`, `brands.is_active = TRUE`를 모두 만족한 상품만 새 게임에 참가한다.
- 서버가 8강 또는 16강 대진을 중복 없이 구성하며 클라이언트는 현재 경기의 승자만 제출한다.
- 완료된 플레이만 통계에 포함한다. 익명 사용자의 재참여는 허용하며 고유 사용자 수를 집계하는 것은 아니다.
- 검색 API 전체의 DB 전환은 별도 작업으로 둔다.

### 공통 계약

- 상품 ID는 PostgreSQL `BIGINT`를 손실 없이 전달하도록 양의 정수 문자열로 표현한다. 세션·경기 ID는 UUID로 사용한다.
- 상태는 `IN_PROGRESS`, `COMPLETED`, `ABANDONED`, `EXPIRED` 네 가지다. 종료 상태에서 진행 상태로 되돌아가지 않는다.
- 세션 만료는 초기 기본값으로 생성 후 24시간을 제안한다. 활동 시 연장하지 않으며 설정값으로 관리한다. 완료한 세션에는 진행 만료를 적용하지 않는다.
- 오류 응답 형식은 `{ "error": { "code": "...", "message": "..." } }`로 통일한다.
- 입력 형식 오류는 400, 익명 쿠키 누락은 401, 없는 세션 또는 다른 소유자의 세션은 동일한 404, 상태 충돌은 409, 진행 만료는 쓰기 API에서 410으로 처리한다.
- DB 연결 실패는 503, 예상하지 못한 오류는 500으로 응답한다. DB 접속 정보는 응답·로그에 노출하지 않는다.
- 쿠키는 HttpOnly, 운영 환경에서는 Secure, SameSite=Lax로 설정한다. 쓰기 요청은 허용된 출처인지 확인한다.
- 소유권은 쿠키 토큰의 해시와 세션의 `owner_token_hash`로 확인한다. 세션 ID만으로 조회·변경할 수 없다.
- 세션 응답은 아래 필드를 공통 사용한다. 해당하지 않는 `currentMatch`, `winner`는 null이다.

```json
{
  "sessionId": "<UUID>",
  "status": "IN_PROGRESS",
  "roundSize": 8,
  "expiresAt": "<ISO 8601>",
  "progress": {
    "completedMatches": 0,
    "totalMatches": 7,
    "currentRoundSize": 8,
    "roundMatchNumber": 1,
    "roundMatchCount": 4
  },
  "currentMatch": {
    "id": "<UUID>",
    "left": { "productId": "1", "name": "빅맥", "brandName": "맥도날드", "description": "...", "imageUrl": null },
    "right": { "productId": "5", "name": "와퍼", "brandName": "버거킹", "description": "...", "imageUrl": null }
  },
  "winner": null
}
```

`completedMatches`는 승자가 확정된 전체 경기 수, `totalMatches`는 최초 강수 − 1이다. 종료 상태에서는 현재 라운드 관련 필드와 `currentMatch`를 null로 반환한다. 위 UUID·시각은 형식 설명용 자리표시자다.

## API 1. 참가 옵션 조회

### 목적과 선행 작업

`GET /api/worldcup/options`

시작 화면에 실제 참가 가능 상품 수와 가능한 강수를 제공한다. 이 단계에는 월드컵 테이블이 필요하지 않다. 기존 DB 연결 확인과 상품 조회 모듈만 구현한다.

계획 작성 당시 `backend/src/db/pool.ts`에 접속 자격증명을 포함한 기본 문자열이 있었다. 실제 구현 전에 노출된 비밀번호를 교체하고 기본값을 제거하여 `DATABASE_URL`로만 연결한다. Git 이력에서 코드가 사라져도 비밀번호가 무효화되는 것은 아니다. TLS 인증서 검증, 풀 크기·타임아웃, 테스트용 DB 분리도 점검한다. 이 문서에는 자격증명을 기록하지 않는다.

### 입력 및 검증

- 요청 본문과 필수 쿼리는 없다.
- 로그인·익명 쿠키 없이 조회할 수 있다.
- 브랜드·재료 필터는 1차 버전에서 지원하지 않는다.

### 비즈니스 로직

1. 상품을 브랜드·카테고리와 조인한다.
2. 공통 참가 조건을 적용하고 상품 ID 기준으로 중복 없이 개수를 센다.
3. 8개 이상이면 8강, 16개 이상이면 16강을 활성화한다.
4. 참가 수가 0이어도 정상 응답을 반환한다. 데이터 없음과 DB 장애를 구분한다.
5. 조회 시점의 안내일 뿐 참가 자리를 예약하지 않는다. 실제 시작 시 API 2가 같은 조건을 다시 검증한다.

### 데이터 접근 및 응답

읽기 전용이며 세션이나 통계를 생성하지 않는다.

```json
{
  "eligibleProductCount": 18,
  "roundOptions": [
    { "roundSize": 8, "available": true },
    { "roundSize": 16, "available": true }
  ]
}
```

성공은 200이다. 연결 불가 시 503 `DATABASE_UNAVAILABLE`로 응답하고 목업 수치로 대체하지 않는다.

### 검증 및 완료 기준

- 참가 수 0·7·8·15·16·18에서 가능한 강수가 정확하다.
- 비활성 브랜드, 판매 중단 상품, 다른 카테고리는 제외된다.
- DB 장애가 참가 수 0으로 잘못 표시되지 않는다.
- 프론트 연동 시 불가능한 강수를 비활성화하고, 조회 실패에는 재시도를 제공한다.
- 해당 API의 테스트와 백엔드 빌드 통과 후 커밋한다.

## API 2. 월드컵 시작

### 목적과 의존성

`POST /api/worldcup/sessions`

API 1의 참가 상품 조회 조건을 재사용한다. 이 단계에서 세션·참가자·경기 테이블과 생성 요청의 중복 방지 저장소를 마이그레이션으로 추가한다. 전체 상품 시드를 매 배포마다 다시 실행하지 않는다.

### 입력 및 검증

- JSON 본문: `{ "roundSize": 8 }` 또는 `{ "roundSize": 16 }`.
- `Idempotency-Key` 헤더: 클라이언트가 시작 동작마다 생성한 UUID. 동일 요청 재시도에서는 유지한다.
- 정수가 아닌 값, 8·16 외의 값, 잘못된 요청 식별자는 400으로 거절한다.
- 클라이언트가 참가자 목록·승자·대진 순서를 지정할 수 없다.

### 필요한 DB 구조

| 테이블 | 주요 데이터·제약 |
|---|---|
| `worldcup_sessions` | UUID, 소유자 토큰 해시, 최초 강수, 상태, 최종 우승 상품, 생성·완료·중단·만료 시각 |
| `worldcup_entries` | 세션 ID, 상품 ID, 최초 대진 위치, 이름·브랜드·설명·이미지 스냅샷. 세션 내 상품 및 위치 각각 UNIQUE |
| `worldcup_matches` | UUID, 세션 ID, 라운드 강수, 0부터 시작하는 경기 순서, 양쪽 상품, 승자, 결정 시각. 세션·라운드·순서 UNIQUE |
| `worldcup_creation_requests` | 요청 키, 요청 본문 해시, 소유자 해시, 세션 ID, 초기 응답, 제한된 재전송 기한. 요청 키 UNIQUE |

양쪽 상품은 해당 세션의 참가자를 참조하도록 복합 FK를 둔다. 두 상품이 서로 달라야 하며 승자는 양쪽 중 하나여야 한다. 과거 기록이 참조하는 상품은 삭제를 제한하고 상태 변경으로 관리한다.

### 익명 쿠키 부트스트랩

1. 쿠키가 없으면 충분히 무작위인 소유자 토큰을 발급하고 쿠키만 설정한다.
2. 이 응답은 428 `ANONYMOUS_SESSION_REQUIRED`로 반환하며 DB 세션은 생성하지 않는다.
3. 프론트는 쿠키를 받은 뒤 같은 요청 키로 시작 요청을 한 번 재시도한다. 쿠키를 사용할 수 없으면 반복하지 않고 안내한다.
4. DB 쓰기는 쿠키가 있는 요청부터 수행한다. 따라서 첫 응답 유실로 소유권 없는 세션이 생성되지 않는다.

### 비즈니스 로직과 트랜잭션

1. 요청 형식·출처·쿠키를 검증하고 생성 빈도 제한을 적용한다.
2. 동일 요청 키가 이미 있는지 확인한다. 같은 소유자·같은 본문이면 기존 초기 응답을 반환한다. 다른 본문이면 409 `IDEMPOTENCY_KEY_REUSED`, 다른 소유자이면 기존 세션 정보를 노출하지 않고 충돌 오류를 반환한다.
3. 새 요청이면 트랜잭션을 시작하고 요청 키의 UNIQUE 제약으로 동시 생성을 차단한다. 경쟁 요청은 기존 작업의 완료 후 저장된 결과를 재사용한다.
4. 하나의 일관된 조회 결과에서 참가 조건을 만족하는 상품 목록을 가져온다. 옵션 조회 이후 상품이 비활성화됐을 수 있으므로 개수를 다시 확인한다.
5. 부족하면 409 `INSUFFICIENT_PRODUCTS`로 실패시키고 전체 롤백한다.
6. 상품 목록을 서버에서 균등하게 섞어 강수만큼 추출한다. 같은 상품은 한 번만 참가한다.
7. `IN_PROGRESS` 세션과 참가자 스냅샷을 저장한다. 이미지가 없으면 null로 저장하고 프론트가 공통 이미지로 대체한다.
8. 추출 순서에서 0·1번, 2·3번 식으로 첫 라운드 대진을 생성한다. 8강은 4경기, 16강은 8경기다. 다음 라운드는 아직 만들지 않는다.
9. 초기 응답과 요청 키를 같은 트랜잭션에서 저장하고 커밋한 뒤 201을 반환한다.

### 응답 및 재시도

- 최초 생성: 201, 공통 세션 응답과 첫 경기.
- 같은 키·본문의 재전송: 200, 저장된 초기 응답. 최신 진행 상태가 필요하면 API 3을 호출한다.
- 응답 유실 후에도 같은 세션 ID를 반환한다. 이미 진행한 세션의 초기 응답으로 진행 상태를 덮어쓰지 않도록 프론트는 저장된 세션이 있으면 API 3으로 복원한다.
- 새 게임은 새로운 요청 키로 시작한다. 기존 진행 세션을 이 API에서 자동 종료하지 않는다.
- 생성 요청 기록은 최소 세션 진행 유효기간 동안 유지하고 이후 보관 정책으로 정리한다.

### 검증 및 완료 기준

- 선택한 강수만큼 참가자가 생성되고 첫 라운드 수가 맞다.
- 잘못된 강수·참가 부족에서 어떤 세션도 부분 저장되지 않는다.
- 최초 쿠키 발급 요청은 세션을 생성하지 않는다.
- 같은 키의 연속·동시 요청은 세션 한 개만 생성한다.
- 중간 INSERT 실패 시 요청 기록·참가자·경기 모두 롤백된다.
- 기존 프론트 게임은 유지한 채 API 테스트로 생성 응답까지 검증하고 커밋한다.

## API 3. 진행 상태 조회

### 목적과 의존성

`GET /api/worldcup/sessions/:id`

API 2의 데이터를 읽어 새로고침이나 응답 유실 후 현재 상태를 복원한다. 게임을 진행하거나 다음 라운드를 만드는 책임은 없다.

### 입력 및 검증

- `id`는 UUID여야 한다. 형식 오류는 400.
- 소유자 쿠키 누락은 401.
- 존재하지 않거나 다른 소유자의 세션은 동일한 404 `SESSION_NOT_FOUND`.

### 비즈니스 로직

1. 소유권 조건을 포함해 세션을 조회한다.
2. 세션·경기·참가자를 하나의 일관된 DB 스냅샷에서 읽는다. 여러 쿼리를 쓰면 읽기 전용 REPEATABLE READ 트랜잭션을 사용한다.
3. 저장 상태가 진행 중인데 서버 시각이 만료 시각 이상이면 응답 상태를 `EXPIRED`로 계산한다. GET에서는 DB를 수정하지 않는다.
4. 진행 중이면 생성된 최신 라운드에서 아직 선택하지 않은 경기 중 가장 앞의 경기를 반환한다.
5. 카드 표시 정보는 시작 당시 참가자 스냅샷에서 가져온다. 시작 이후 판매 상태가 바뀌어도 대진을 다시 추첨하지 않는다.
6. 완료 상태이면 최종 우승 상품의 스냅샷과 완료 시각을 반환한다.
7. 중단·만료 상태이면 현재 경기와 우승자를 null로 반환한다. 선택 완료 경기 수는 유지한다.
8. 진행 상태인데 현재 경기가 없거나 완료 상태에 우승자가 없는 등 불변식이 깨졌으면 500 `INVALID_SESSION_STATE`로 기록하고 임의 복구하지 않는다.

### 응답 및 예외

소유자가 조회한 세션은 종료·만료 상태도 200으로 반환한다. 쓰기 API의 만료 410과 구분한다. 동일 조회를 반복해도 상품·대진·경기 수가 달라지지 않는다. 개인정보 성격의 진행 응답에는 `Cache-Control: private, no-store`를 사용한다.

### 검증 및 완료 기준

- 생성 직후 첫 경기와 완료 경기 수 0을 반환한다.
- 테스트 데이터로 중간 라운드·우승·중단·만료 상태를 각각 검증한다.
- 쿠키 없는 요청과 다른 소유자 접근을 차단한다.
- 투표와 조회가 동시에 실행돼도 이전 또는 이후의 일관된 상태를 반환한다.
- 반복 GET이 DB 값을 변경하지 않는다.
- 복원 응답 계약을 검증하고 커밋한다. 실제 화면의 복원 연결은 선택 API 준비 후 진행한다.

## API 4. 경기 선택 및 다음 단계 진행

### 목적과 의존성

`POST /api/worldcup/sessions/:id/matches/:matchId/vote`

API 2의 대진과 API 3의 상태 응답을 사용한다. 이 API 하나가 선택 저장, 다음 라운드 생성, 결승 완료를 담당한다. 별도의 ‘우승자 저장 API’는 만들지 않는다.

### 입력 및 검증

- 세션·경기 ID: UUID.
- 본문: `{ "winnerProductId": "3" }`.
- 상품 ID는 양의 정수 문자열인지 검증한다.
- 소유권과 요청 출처를 검사하고 과도한 반복 요청은 429로 제한한다.
- 경기 ID는 반드시 해당 세션에 소속되어야 한다.

### 비즈니스 로직: 트랜잭션과 판단 순서

1. 트랜잭션을 시작하고 소유권 조건으로 세션 행을 `SELECT ... FOR UPDATE`하여 잠근다.
2. 해당 세션의 경기인지 확인한다. 없으면 404 `MATCH_NOT_FOUND`.
3. 이미 승자가 저장된 경기인지 먼저 확인한다.
   - 같은 상품 재선택: 쓰기 없이 200, `replayed: true`와 최신 세션 상태 반환.
   - 다른 상품 재선택: 409 `MATCH_ALREADY_DECIDED`.
   - 완료·중단·만료 이후라도 과거 성공 요청의 동일 재전송은 성공 사실을 반환한다. 새 선택을 허용하는 것은 아니다.
4. 아직 결정되지 않은 경기라면 세션 상태를 검사한다.
   - 완료·중단: 409 `SESSION_NOT_PLAYABLE`.
   - 저장 상태가 만료이거나 시각상 만료: 필요하면 `EXPIRED`를 저장·커밋한 뒤 410 `SESSION_EXPIRED` 반환. 오류 응답 때문에 만료 저장까지 롤백하지 않도록 구분한다.
5. 서버가 계산한 현재 경기와 요청 경기 ID가 일치하는지 확인한다. 다음 경기를 건너뛰는 요청은 409 `NOT_CURRENT_MATCH`.
6. 선택 상품이 양쪽 참가자 중 하나인지 확인한다. 아니면 400 `INVALID_WINNER`.
7. 승자와 결정 시각을 저장한다.
8. 아래 세 가지 진행 분기에 따라 상태를 계산한다.
9. 모든 변경을 커밋한 뒤 공통 세션 응답과 `replayed: false`를 반환한다.

### 분기 A: 같은 라운드에 미진행 경기 존재

현재 라운드에서 다음 순서의 미결정 경기를 반환한다. 다음 라운드는 생성하지 않는다. 전체 완료 경기 수는 정확히 1 증가한다.

### 분기 B: 라운드의 마지막 경기이고 결승이 아님

1. 현재 라운드의 모든 승자를 `match_index` 순서로 읽는다.
2. 승자 수가 현재 라운드 강수의 절반인지 확인한다.
3. 0·1번째 승자, 2·3번째 승자를 묶는다. 다음 라운드에서 다시 섞지 않는다.
4. 다음 라운드 강수를 절반으로 줄이고 경기들을 생성한다.
5. 다음 라운드 첫 경기를 반환한다.

예: 8강의 네 승자 A·B·C·D → 4강 A 대 B, C 대 D. 세션 잠금과 경기 UNIQUE 제약으로 다음 라운드의 중복 생성을 막는다.

### 분기 C: 결승 종료

1. 결승 승자를 최종 우승자로 지정한다.
2. 총 확정 경기 수가 최초 강수 − 1인지 검증한다. 8강은 7, 16강은 15다.
3. 세션을 `COMPLETED`로 변경하고 `winner_product_id`, `completed_at`을 저장한다.
4. `currentMatch: null`, 최종 `winner`를 반환한다.
5. 랭킹 누적 카운터는 증가시키지 않는다. API 6이 완료 세션을 집계하므로 재시도로 통계가 중복 증가하지 않는다.

### 실패 처리와 프론트 연결

선택·라운드 생성·완료 처리 중 하나라도 실패하면 전체 롤백한다. 재시도는 같은 경기 ID와 승자 ID로 보낸다. 요청 중 카드 클릭을 막고 성공 응답이 올 때만 다음 화면으로 전환한다. 통신 실패 시 현재 경기와 선택을 보존한다. 서버에서 이미 진행된 상태가 확인되면 API 3으로 동기화한다.

### 검증 및 완료 기준

- 8강·16강 전체 경기가 올바른 대진으로 끝난다.
- 같은 선택의 동시 요청은 한 번만 저장된다.
- 서로 다른 동시 선택에서는 하나만 성공하고 나머지는 409다.
- 다른 경기·미래 경기·다른 세션 상품을 제출해도 상태가 바뀌지 않는다.
- 결승 성공 응답 유실 후 재시도해도 동일 우승 결과를 반환한다.
- 다음 라운드 INSERT 또는 완료 UPDATE 실패 시 현재 선택도 롤백된다.
- 이 API의 테스트와 빌드를 완료하고 별도 커밋한다.

## API 5. 월드컵 중단

### 목적과 의존성

`POST /api/worldcup/sessions/:id/abandon`

진행 중인 월드컵을 명시적으로 종료한다. 기록 삭제나 결과 취소 API가 아니다. API 4와 동일한 세션 잠금 규칙을 사용한다.

### 입력 및 검증

본문은 없다. 세션 UUID, 익명 쿠키, 소유권, 요청 출처를 검증한다.

### 비즈니스 로직

1. 트랜잭션에서 세션 행을 잠그고 소유권을 확인한다.
2. 이미 `ABANDONED`면 200으로 기존 상태를 반환한다. 반복 호출해도 종료 시각을 변경하지 않는다.
3. `COMPLETED`면 409 `SESSION_ALREADY_COMPLETED`. 우승 결과나 랭킹을 취소하지 않는다.
4. 진행 중이지만 만료 시각을 지났거나 이미 `EXPIRED`면 만료 상태를 반환한다. 필요한 만료 상태 변경을 커밋하고 410으로 응답한다.
5. 유효한 `IN_PROGRESS`이면 `ABANDONED`로 변경하고 `abandoned_at`을 저장한다.
6. 참가자와 기존 경기 결과는 보존한다. 미진행 경기는 승자 없이 남기며 이후 선택을 금지한다.
7. 커밋 후 현재 경기·우승자가 null인 공통 세션 응답을 200으로 반환한다.

### 투표와 동시 실행될 때

- 중단이 먼저 잠금을 얻으면 이후 새 투표는 거절된다.
- 일반 경기 투표가 먼저 완료되면 그 결과까지 보존하고 중단한다.
- 결승 투표가 먼저 완료되면 중단은 409로 실패하고 완료 상태가 유지된다.

### 프론트 연결 및 완료 기준

- 사용자에게 종료 확인을 받은 경우에만 호출한다.
- 성공하면 저장된 활성 세션 ID를 해제하고 시작 화면 또는 검색 화면으로 이동한다.
- 실패하면 실패 이유와 재시도 방법을 보여주고, 완료 충돌이면 API 3으로 상태를 갱신한다.
- 단순 탭 닫기는 중단 API 성공을 보장하지 않는다. 남은 세션은 만료 시각으로 판정한다.
- 중단 재시도, 중단 이후 투표, 결승과 중단의 경쟁, 다른 소유자의 중단 시도를 검증한다.
- API 5 완료 후 API 1~5의 프론트 흐름을 연결하고 검증한다. 이 단계에서도 랭킹은 별도 작업으로 남긴다.

## API 6. 월드컵 랭킹 조회

### 목적과 의존성

`GET /api/worldcup/rankings`

API 4에서 완료한 세션만 대상으로 실제 랭킹을 계산한다. 로그인 없이 조회 가능하며 DB를 수정하지 않는다.

### 입력 및 기본값

| 쿼리 | 허용 값·기본값 |
|---|---|
| `sort` | `championships` 또는 `winRate`, 기본 `championships` |
| `roundSize` | 생략 시 전체, 지정 시 8 또는 16 |
| `q` | 상품 이름 부분 검색, 앞뒤 공백 제거, 최대 100자 |
| `page` | 1 이상의 정수, 기본 1 |
| `pageSize` | 1~100 정수, 기본 20 |

잘못된 정렬·강수·페이지 값은 400이다. 검색문은 SQL 매개변수로 전달하며 `%`, `_`도 일반 검색 문자로 취급하도록 이스케이프한다.

### 비즈니스 로직: 집계 대상 및 공식

| 지표 | 계산 |
|---|---|
| `championships` | 최종 우승 상품이 해당 상품인 완료 세션 수 |
| `appearances` | 해당 상품이 참가한 완료 세션 수 |
| `matches` | 완료 세션에서 해당 상품이 치른 경기 수 |
| `wins` | 해당 상품이 승자인 경기 수 |
| `winRate` | `wins / matches × 100`, 대결 수 0이면 null |

1. `COMPLETED` 세션만 선택하고 `roundSize` 조건을 먼저 적용한다.
2. 상품별 우승, 참가, 경기·승리 수를 각각 따로 집계한다. 참가자·경기를 한 번에 조인해 우승 수가 부풀려지지 않도록 한다.
3. 현재 참가 가능한 상품과 선택 범위의 완료 기록에 등장한 과거 상품을 합쳐 조회 대상 상품 집합을 만든다. 판매 중단 상품도 기록이 있으면 상태와 함께 표시한다.
4. 상품 ID로 집계값을 결합한다. 이름·브랜드는 현재 상품 정보로 표시하고 과거 세션 화면만 스냅샷을 사용한다.
5. 정렬 기준의 원본 값으로 전체 순위를 계산한다. 동률은 `RANK()` 방식으로 1·2·2·4위가 된다. 상품 ID는 표시 순서를 안정화할 때만 사용하며 동률 판정에 포함하지 않는다.
6. 승률은 부동소수점·화면 반올림 값으로 순위를 정하지 않는다. 정수 승리·대결 수를 기반으로 일관된 DB 수치 계산을 사용한다. 표시만 소수점 한 자리로 반올림한다.
7. 대결 수가 0인 상품의 순위는 null로 두고 집계가 있는 상품 뒤에 표시한다. 승률 최소 경기 수 제한은 최초 버전에서는 적용하지 않고 대결 수를 함께 표시한다.
8. 검색 전에 TOP 3를 추출한다. 공동 3위까지 포함하므로 카드가 3개를 넘을 수 있다.
9. 전체 순위를 유지한 채 이름 검색을 적용하고 마지막에 페이지네이션한다. `totalCount`는 검색 후·페이지 적용 전 상품 수다.
10. TOP 3·전체 목록·카운트는 같은 읽기 스냅샷으로 반환한다. SQL 조회는 파라미터 바인딩을 사용한다.

### 응답 예시

```json
{
  "sort": "championships",
  "roundSize": null,
  "page": 1,
  "pageSize": 20,
  "totalCount": 18,
  "completedSessionCount": 10,
  "leaders": [
    { "productId": "1", "name": "빅맥", "brandName": "맥도날드", "imageUrl": null, "status": "ACTIVE", "rank": 1, "championships": 4, "appearances": 8, "matches": 17, "wins": 13, "winRate": 76.5 }
  ],
  "items": [
    { "productId": "1", "name": "빅맥", "brandName": "맥도날드", "imageUrl": null, "status": "ACTIVE", "rank": 1, "championships": 4, "appearances": 8, "matches": 17, "wins": 13, "winRate": 76.5 }
  ]
}
```

예시는 필드 설명을 위해 배열을 축약한 것이다. 실제 응답의 상품 수와 순위는 DB 집계 결과를 따른다.

완료 세션이 하나도 없으면 `completedSessionCount: 0`, `leaders: []`, 상품별 0회·승률 null·순위 null을 반환한다. 화면은 이 값을 이용해 첫 참여 안내를 표시한다. 검색 결과가 없으면 `items: []`, `totalCount: 0`을 반환하며 전체 통계와 TOP 3는 유지한다. 범위를 벗어난 페이지는 빈 목록을 200으로 반환한다.

### 성능 및 프론트 연결

세션 상태·최초 강수, 경기의 세션 ID, 참가자의 상품 ID에 필요한 인덱스를 점검한다. 최초 구현에서는 원본 집계를 사용하고 실제 실행 계획을 확인한 뒤 캐시·통계 테이블 도입을 검토한다.

랭킹 화면의 목업 통계를 이 API로 교체하고 검색·정렬·페이지 변경마다 조회한다. 랭킹 메뉴는 추가하지 않으며 월드컵 시작·완료 화면의 ‘랭킹 확인하기’ 버튼을 유지한다. 요청 실패 시 이전 데이터를 실제 최신 결과로 오인하게 하지 않도록 오류 상태를 표시한다.

### 검증 및 완료 기준

- 완료·진행·중단·만료 세션이 섞인 데이터에서 완료 기록만 집계한다.
- 여러 참가자·경기 조인으로 우승 횟수가 증가하지 않는다.
- 8강·16강 필터 적용 시 모든 통계의 모집단이 동일하다.
- 공동 순위, 반올림 전 순위, 대결 0회, 판매 중단 상품을 검증한다.
- 검색 후 순위 유지, 페이지 경계, 검색 결과 없음, 전체 완료 기록 없음을 검증한다.
- TOP 3는 검색 및 페이지에 영향을 받지 않으며 공동 3위까지 포함한다.
- 결승 저장 직후 재조회에서 완료 기록이 정확히 한 번 반영된다.
- 프론트 목업 제거와 조회 연결까지 검증하고 해당 API 작업을 커밋한다.

## API별 공통 완료 체크리스트

각 API 작업에 아래 체크리스트를 적용한다. 후속 API 전체를 완성해야 현재 작업을 커밋할 수 있는 구조로 만들지 않는다.

- [ ] 해당 API의 요청·응답·오류 계약 구현
- [ ] 필요한 DB 변경만 별도 마이그레이션으로 추가
- [ ] 정상·예외·소유권 테스트 통과
- [ ] 쓰기 API는 중복·동시 요청·롤백 테스트 통과
- [ ] 기존 검색·랜덤 추천 기능에 영향이 없는지 확인
- [ ] 변경 범위에 맞는 빌드·타입 검사 실행
- [ ] API 명세와 실제 동작 일치 여부 확인
- [ ] `status: 한글 커밋 메시지` 형식으로 개별 커밋

전체 API 연결 후에는 `npm run build`와 시작 → 새로고침 복원 → 경기 선택 → 우승 → 랭킹, 중도 종료 → 재시작 흐름을 확인한다. 운영 DB 적용은 테스트 DB 검증 후 진행한다. 중단·만료 기록의 보관 기간 및 정리 작업은 운영 전 별도 확정한다.
